# `@rhwp/*` 텍스트 배치 회귀 — 원인과 검증 방법

**결론(2026-08-13 개정): `@rhwp/core` 는 `0.8.4`. 아래 분석의 기전은 맞지만 버전 귀속이 틀렸었다 —
호스트 계측 콜백이 사라진 것은 0.8.x 가 아니라 `0.7.3` → `0.7.18` 사이다.**

업스트림 이슈: [edwardkim/rhwp#4701](https://github.com/edwardkim/rhwp/issues/4701) (2026-08-13 제출)
— **마침표로 제출했으나 메인테이너 검증으로 가운뎃점(U+00B7)으로 재분류됨.** 아래 §정정-2 참조.
임베드 환경 구조 개선 제안은 [#4709](https://github.com/edwardkim/rhwp/issues/4709) 로 분리.

## ⚠️ 2026-08-13 정정 — 회귀가 들어온 시점

이 문서는 `0.7.3` 기준선에서 작성됐고, 당시 브랜치에는 `0.7.18` 업그레이드가 없었다. 아래 §110 이
"0.7.3 → 0.7.19 사이에 같은 회귀가 들어왔는지 미검증"이라 남겨둔 항목을 실측으로 닫는다.

npm 패키지에서 `globalThis.measureTextWidth` 참조 수:

| `@rhwp/core` | 0.7.3 | **0.7.18** | 0.8.2 | 0.8.4 |
|---|---|---|---|---|
| `measureTextWidth` 참조 | 2 | **0** | 0 | 0 |

**콜백 제거는 0.7.18 에 이미 들어와 있었다.** 즉 2026-07-16 부터 우리 운영본은 내부 메트릭 방식이었고,
"0.8.x 만의 회귀"가 아니다. `rhwp-version-diff.mjs` 로 `biz_plan.hwp` 1p advance 재측정:

| 글자 | 0.7.3 (호스트 계측) | 0.7.18 (당시 운영본) | 0.8.4 |
|---|---|---|---|
| `.`@18.7 | 5.97 | 14.76 | 15.45 |
| `-`@26.7 | 28.00 | 35.55 | **28.72** |
| `1`@18.7 | 10.27 | 10.88 | **10.55** |

아래 §실측 표의 "0.8.2" 열 수치(`.` 14.76, `-` 35.55, `1` 10.88)는 **0.7.18 과 동일**하다.

⚠️ **위 표의 값을 "advance" 로 읽지 말 것.** `x[i+1] - x[i]` 는 사이의 공백·자동번호 여백을 통째로
포함한다 — 그래서 같은 `.` 이 2 페이지에서 8 가지 값(12.84 ~ 16.23)으로 갈린다. 폰트 advance 는
같은 글자·크기면 상수이므로, 이 표는 advance 표가 아니라 **"구간 폭" 표**다. §정정-2 참조.

에디터 렌더 경로(canvaskit)는 별개로 개선됐다. 재현본(`상장양식.hwpx`, 원본 XML `{이름}` 공백 없음):

| | 0.7.18 | 0.8.2 | 0.8.4 |
|---|---|---|---|
| 렌더 | `{ 이름}` ❌ | `{ 이름}` ❌ | `{이름}` ✅ |

7/30 에 0.8.2 를 롤백한 "유령 한 칸"은 0.8.2 가 만든 게 아니라 0.7.18 부터 있었다.

## ⚠️ 2026-08-13 정정-2 — 원인은 마침표가 아니라 가운뎃점(U+00B7)

#4701 에 마침표(U+002E) 건으로 제출했고, 메인테이너(planet6897)가 한글 출력본 PDF 와 글리프 origin
대조로 검증해 **귀속이 틀렸음**을 지적했다. 우리 측정값은 전부 정확했고 해석이 틀렸다. 그쪽 결론을
우리 도구로 재검증해 확인했다.

### 무엇이 틀렸나 — `1.` 은 문단 자동 번호였다

`1.사업명` 의 `1.` 은 본문 run 텍스트가 아니라 문단 자동 번호다. SVG 는 공백·번호 여백에 `<text>` 를
내보내지 않으므로 `x[i+1] - x[i]` 가 그 여백을 삼킨다.

```
15.453px  =  마침표 6.413  +  자동번호 여백 9.040
```

마침표 단독 advance 는 `0.3436 em` 으로 표값 `HAANSOFT_BATANG_ASCII['.'] = 0.3440` 과 일치한다.
**2.6 배가 아니었다.** 우리 데이터로도 확인된다 — 2 페이지에서 같은 `.` 의 구간 폭이 8 가지
(12.840 / 13.134 / 13.267 / 14.810 / 14.840 / 15.292 / 15.453 / 16.227) 로 갈린다.

### 전제가 뒤집힌 지점 — 0.7.3 은 오라클이 아니다

"0.7.3(5.97) 이 브라우저 실측(5.98) 과 일치한다" 를 근거로 0.7.3 을 정답으로 놓았는데, **둘 다 자동번호
여백을 무시했기 때문에 일치한 것**이다. 한글은 그 여백을 넣는다. 한글 PDF 대조:

| | 한글 PDF 대비 |
|---|---|
| 0.8.4 | **+0.14px** (거의 일치) |
| 0.7.3 | **−9.3px** (여백을 흘림) |

**교훈: 서로 다른 두 측정이 같은 맹점을 공유하면 일치해도 검증이 아니다.** 이 문서가 원래 하이픈을
"공백 오염 의심" 으로 제외했던 그 사유가 마침표 쌍에도 그대로 해당했다.

### 진짜 결함 — 가운뎃점 `·` (U+00B7)

| 출처 | advance/em |
|---|---|
| 한글 PDF (동일 페이지 581 개 실측) | 0.3192 |
| 브라우저 `measureText` | 0.3198 |
| **rhwp 0.8.4** (`haansoft_latin_override`) | **0.3329** |

**+4.1%**, 목차 줄마다 `·` 가 **85 개** 이어지므로 줄 끝에서 **약 +21px** 누적된다. 우리가 보고한
"최대 Δx 31.60px / 634 of 642 글리프 어긋남" 의 실질적 주범이 이것이다. 우리 표에 `·` 6.21 이 이미
잡혀 있었으나 이 항목만 85 배로 누적된다는 점을 놓쳤다.

우리 재검증(0.8.4, `biz_plan.hwp` 1p): `·→·` 581 쌍 평균 **0.3329 em**, 목차 줄당 `·` **85 개** —
메인테이너 수치와 일치.

메인테이너 교정 실험(`·`·`.` → 0.3198): 2 페이지 최대 오차 **22.19px → 1.13px**.
기여도는 `·` 20.9px/줄, `.` 0.45px/줄로 사실상 전부 가운뎃점.

### 더 큰 단서 — ASCII 표 전체의 계통 오차 → **확정됨**

폭 표는 "한국어 전각을 1.0 기준으로 정규화해 전역 장평 97% 를 지운다" 는 절차로 만들어졌는데,
0.970 이 폰트의 고유 advance 라면 그 나눗셈이 전 ASCII 값을 약 3% 부풀린다. 잔차가 `·` +4.1%,
`1` +3.0%, `.` +5.8% 로 **전부 한 방향**인 것이 이를 뒷받침한다.

우리가 ASCII 95 자 전수 실측표를 올린 뒤(#4701) 메인테이너가 `fontTools` 로 `HANBatang.ttf` 의
hmtx 를 직접 읽어 독립 검증했고, **원인이 확정됐다.**

- 우리 실측값과 hmtx 판독값이 16 자 표본에서 전수 일치, 통계(중앙값 1.0357 / 1Q 1.0275 / 3Q 1.0441
  / 최대 1.0750 / 1÷0.970 ±0.005 구간 27 자)도 그대로 재현. upm = 1000 도 head 테이블에서 확인.
- `·` 와 `.` 은 advance·lsb 가 `320/110` 으로 **완전히 동일한 글리프**다 — 표가 둘을 0.3330/0.3440 으로
  갈라놓은 것 자체가 잡음의 증거.
- 성분 분해가 깔끔하다:

| 대조 | hmtx 대비 평균 편차 |
|---|---|
| 표 그대로 | 3.54% |
| 표 × 0.970 | **1.11%** |

즉 **3.54% 중 3.09%p 가 전각 정규화 나눗셈**이고, 남는 약 1.1% 가 위 §발견①의 추출 잡음이다.

### 교정 경로 — 표를 새로 만들 필요가 없다

rhwp 에 이미 TTF 에서 자동 추출된 정확한 표가 있다(`font_metrics_data.rs`). `FONT_0_LATIN_0`
(U+0020~U+007E) 는 hmtx 와 **불일치 0 자**, `FONT_0_LATIN_1` 의 U+00B7 도 320 으로 정확하다.
`haansoft_latin_override` 가 함초롬바탕에 한해 그 정확한 값을 가로채고 있는 구조다.
따라서 교정은 표 재생성이 아니라 **override 를 걷어내 자동 생성 표로 되돌리는 것**이다.

배열 이름 `HAANSOFT_BATANG_ASCII`(한컴바탕 대체)는 §4.31 이 내용물을 HCRBatang 측정값으로
갈아끼운 뒤로 이름만 남은 상태이며, #2156 의 "함초롬바탕 라틴은 한컴바탕 메트릭으로 렌더한다" 는
전제는 실질적으로 폐기됐다. 업스트림이 이름까지 정리하기로 했다.

**굵기 주의:** 우리가 "Bold ASCII advance 는 Regular 와 동일" 이라 보고한 것은 표본이 10 자여서
생긴 과일반화였다. 95 자 중 **`k`(0.5820→0.5800), `q`(0.5790→0.5970) 2 자가 다르다**
(우리 브라우저 측정으로도 동일 값 재현). 현행 `haansoft_latin_override` 는 bold 인자를 받지 않아
`q` 에서 1.8% 가 남으므로, hmtx 전환 시 굵기별 조회로 함께 교정된다.
"Bold 표본으로 만들어진 표는 아니다" 라는 기각 결론 자체는 유효하다(비율 중앙값이 Regular 와 동일).

**쪽수 영향:** §4.31 자신이 A/B 를 돌려 "ASCII 폭을 20~70% 바꿔도 공통 8,544 문서에서 쪽수 다름 0"
을 기록했다(저장 lineseg 가 computed pitch 를 우회하는 문서가 대다수). 이번 교정도 페이지네이션은
움직이지 않을 가능성이 높고, 실익은 줄 안쪽 정합(목차 줄 끝 약 21px)이다. 업스트림은 선례대로
10k 쪽수 게이트를 통과시킨 뒤 제출하며, 다른 건의 게이트가 완주한 뒤 순서로 진행한다.

### 우리 쪽 실제 영향

- **0.8.4 업그레이드 판단은 강화됐다** — 문제로 지목된 자리에서 0.8.4 가 한글과 0.14px 차이다.
- 목차처럼 점선 리더가 있는 문서는 미리보기(`renderPageSvg`)에서 줄 끝이 약 21px 밀린다.
  실존 증상이며 #4701 로 업스트림이 추적한다.
- 교정은 페이지네이션에 영향을 주므로 업스트림이 대규모 쪽수 게이트 후 반영한다. 우리가 할 일은 없다.

## 증상

문단 앞부분(번호·마침표 등 라틴/구두점 구간)에서 **공백 한 칸이 삽입된 것처럼** 이후 텍스트가 오른쪽으로 밀린다. 점선 리더(`·`)가 이어지는 줄은 편차가 누적돼 줄 끝에서 최대 **약 30px** 까지 벌어진다.

우리 앱과 업스트림 데모 양쪽에서 동일하게 재현된다. 즉 **우리 통합 문제가 아니라 업스트림 회귀**다.

## 실측

`public/editor/samples/biz_plan.hwp` 1페이지를 두 버전으로 `renderPageSvg(1)` 한 뒤, `<text>` 글리프를 순서대로 1:1 대응시켜 비교했다.

글리프 642개, **텍스트 내용은 100% 일치**(문서 모델은 동일). 그런데 **631개(98.4%)** 의 x 좌표가 어긋난다.

## 원인

`rhwp.js` 의 wasm-bindgen import 를 비교하면 **글자폭 계측 방식이 바뀌었다.**

**0.7.3 — 호스트에 계측을 위임**

```js
__wbg_measureTextWidth_0962d94b80b2a16a: function(arg0, arg1, arg2, arg3) {
  const ret = globalThis.measureTextWidth(
    getStringFromWasm0(arg0, arg1),   // fontSpec
    getStringFromWasm0(arg2, arg3),   // text
  );
  ...
}
```

스튜디오는 이 콜백을 `ctx.font = <SVG 에 넣을 폰트 스택>; ctx.measureText(text).width` 로 구현한다. **계측에 쓴 폰트와 렌더링할 폰트가 같은 문자열**이므로 배치가 항상 자기 일관적이다.

**0.8.2 — 내부 메트릭으로만 계산**

`measureTextWidth` 참조가 **0개**. Chromium 에서 `renderPageSvg()` 실행 중 `CanvasRenderingContext2D` 와 `OffscreenCanvasRenderingContext2D` 양쪽의 `font` setter 및 `measureText` 를 후킹해 계수한 결과:

```
ctx.font 설정 횟수 : 0
measureText 호출   : 0
```

렌더 경로에서 **브라우저 폰트 계측을 전혀 하지 않는다.** 배치는 WASM 내장 메트릭으로만 계산된다(`rhwp_bg.wasm` 3.68 MB → 7.19 MB).

그런데 출력 SVG 에는 여전히 브라우저가 해석할 폰트 스택이 찍히고, 0.8.2 에서 이게 크게 확장됐다:

```
0.7.3: 함초롬바탕,'Batang','바탕','AppleMyungjo','Noto Serif KR',serif
0.8.2: 함초롬바탕,'Batang','바탕','Nanum Myeongjo','AppleMyungjo','Noto Serif KR',
       'Noto Serif CJK KR','HCR Batang Ext-B','함초롬바탕 확장B','HCR Batang Ext',
       '함초롬바탕 확장','HCR Batang','함초롬바탕','Source Han Serif K Old Hangul',serif
```

**배치는 내부 메트릭, 렌더는 브라우저가 고른 폰트** — 둘이 다르면 글리프가 어긋난다. 시스템마다 폰트 해석 결과가 달라지므로 데모 사이트와 임베드 앱 양쪽에서 재현되는 것과도 일치한다. CJK 는 em 정사각 폭이라 대체로 맞고, 폭이 제각각인 라틴·구두점에서 오차가 두드러진다.

## 우회 불가

`renderer: 'canvas2d'` 옵션으로도 안 된다. 계측 자체가 WASM 내부로 들어간 구조라 호스트가 개입할 지점이 없다.

## 업스트림이 고쳤을 때 — 검증 방법

`scripts/rhwp-version-diff.mjs` 로 눈이 아니라 숫자로 확인한다.

```bash
npm i rhwpnext@npm:@rhwp/core@0.8.3           # 검증할 버전을 별칭으로 설치
npm i -D playwright-core                       # 최초 1회
node scripts/rhwp-version-diff.mjs public/editor/samples/biz_plan.hwp 1 --b=node_modules/rhwpnext
node scripts/rhwp-version-diff.mjs public/editor/samples/footnote-01.hwp 1 --b=node_modules/rhwpnext
```

`✅ 배치 동일 — 회귀 없음.` (exit 0) 이 나오면 통과. 그때 비로소 업그레이드를 진행한다.

업그레이드 시에는 **npm 패키지만 올리면 안 된다.** `public/editor/` 도 같은 세대로 재생성해야 한다 — 0.8 의 `@rhwp/editor` 는 iframe 과 capability 협상(v1 handshake, `handshakeTimeoutMs` 기본 1000ms)을 하고, 스튜디오가 `renderer-diagnostics-v1` / `notify-saved-v1` 을 광고하지 않으면 legacy 로 강등된다. 절차는 `/editor-update` (로컬 전용).

## 참고 — 함께 확인한 사실

- `@rhwp/editor` 0.8 의 API 변화는 **순수 추가형**이다(`exportHwp/Hwpx/Hml`, `getHmlSaveState`, `exportHwpVerify`, `notifySaved`, `getRendererDiagnostics`, `loadFile(..., options)`). `RhwpEditor` 가 `private constructor` 가 됐지만 우리는 `createEditor()` 만 쓰므로 무관하다.
- 같은 API 추가분은 대부분 이미 `0.7.19` 에도 들어와 있다. 0.7 라인 내 업그레이드(`0.7.3` → `0.7.19`)는 별개 선택지지만, 그 사이에 같은 회귀가 들어왔는지 미검증이다. 올리려면 위 스크립트로 먼저 확인할 것.
- `renderPageSvg()` 의 페이지 인덱스는 0.7.3 과 0.8.2 가 다르게 동작한다(0.7.3 은 일부 인덱스에서 `measureTextWidth` 부재 시 throw). 비교 시 같은 페이지 번호를 명시할 것.
